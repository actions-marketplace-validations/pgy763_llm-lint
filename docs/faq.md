# 常见问题

## 我的代码明明有问题，为什么没报？

因为这套规则**故意保守**：认不出来的不报。它不做符号解析，也不读依赖的 jar，只看声明处的类型名后缀。所以下面这些情况一定漏：

- `var client = ...` 之后再 `client.prompt()`——看不出类型；
- 链式返回接下去的调用，比如 `factory.get().call()`；
- 跨文件推断：`@Bean` 在 A 文件、注入在 B 文件，各自独立看；
- 反射、动态代理、配置类里拼出来的 Bean；
- Kotlin / Scala 代码（只解析 `.java`）。

「0 个问题」只代表没命中这二十二条模式，不代表代码没问题。漏报是设计取舍：宁可少报，也不要满屏都是「可能是」的提示——那种工具第二次就没人看了。

## 报了但我认为不该报，怎么办？

三个层次，从轻到重：

```java
// 1. 这一行确实没问题：原地压掉，写清理由
// llm-lint:ignore LLM004 网关统一配了 180 秒
SseEmitter emitter = new SseEmitter();

// 2. 整个文件不适用（生成的代码、测试替身）
// llm-lint:ignore-file
```

```yaml
# 3. 这个项目就是这样：写进仓库的配置，有 diff 有 review
rules:
  LLM009: off   # 客户端由基础镜像统一注入，这里看不到超时配置
```

第 3 种最好——下一个人能看到「为什么不报」和「什么时候可以重新打开」。如果判断范围本身写错了（比如某种写法明显该覆盖却没覆盖），欢迎开 issue，那属于规则的 bug。

## 和 SpotBugs / Error Prone / SonarQube 冲突吗？

不冲突，分工不同：

- 它们查的是**语言和通用缺陷**：空指针、资源泄漏、并发、坏味道。它们不知道 `ChatClient` 是什么。
- llm-lint 查的是**LLM 集成里那几种特定故障**：事务里调模型、SSE 超时、记忆共用、token 预算。它对 Java 语义几乎不关心。

所以可以同时开。llm-lint 不要求项目能编译（Error Prone 要求）、也不要求 classpath（SpotBugs 最好有），一个 jar 扫源码目录就能跑。

## 要联网吗？会把我的代码发出去吗？

不联网。整个工具只做两件事：用 JavaParser 解析你给的 `.java` 文件、在 AST 上跑二十二条规则。没有任何 HTTP 客户端，也不会上传代码或统计。

下载 jar 和 action 拉取 release 是唯一需要网络的地方，那是安装，不是运行。

## 支持 Kotlin / Scala 吗？

不支持，只解析 `.java`。混合项目里 Kotlin 那部分会被跳过（`--since` 也不会把 `.kt` 算进去）。

## 大仓库会不会很慢？

源码解析是瓶颈，而它是并行的：默认按 CPU 核数开线程（最多 8 个），输出顺序和串行完全一样。实测 600 个文件（每个都带着十几处问题）在 28 核机器上约 1 秒；单核、冷启动、文件很多时按线性估算就行。

想对比或复现顺序用 `--jobs 1`；机器紧张也可以在 CI 里限制成 `--jobs 2`。

## 默认为什么只拦 error？

为了第一次接入不至于满屏红。warning 级别的规则（`maxTokens` 偏小、`produces` 少 charset、循环里逐个调模型）都是「确实该改，但不至于让构建挂」。

团队准备好了就 `fail-on: warning`，写进 `.llm-lint.yml`，所有人本地也一样。

## 基线会不会越来越旧？

会，所以有 [`--baseline-stats`](baseline.md)：它告诉你旧账还剩多少、哪几条已经修好。修好的条目应该从基线文件里删掉——否则某天同一个问题重新出现，会被当成「旧账」放过去。建议每个迭代清一次。

两条分支各自加了基线条目时，合并会有冲突。处理办法：以 main 的为准合并，然后重跑一次

```bash
java -jar llm-lint.jar --save-baseline .llm-lint.baseline --fail-on never src/main/java
```

它只增不减，重复条目不会重复。

## 规则级别会变吗？

会。默认级别是工具的判断，随版本演进——比如某条 warning 被证明「漏报的代价更大」，下一个版本可能变成 error。

这正是[配置文件只写差异](config.md#只记差异)的原因：你只写「这条关掉」「这条提到 error」，没写的跟着工具走。如果当初把 `LLM007: warning` 抄进配置「固定下来」，默认值改进时你的配置会把它按回去，而且没人记得为什么。

## 它会改我的代码吗？

不会。`--fix` 只把 unified diff 打到标准输出，一个字都不写回工作区：

```bash
java -jar llm-lint.jar --fix src > fix.patch
git apply fix.patch     # 你自己决定应不应该应用
```

目前只有 LLM006（补 charset）和 LLM018（补 `produces`）有补丁，因为这两条改动是纯增量的、语义完全等价。别的规则要么得挪代码、要么得改设计，不适合自动改。

## 怎么加一条规则？

规则是纯函数：拿到 `CompilationUnit`，返回 `List<Finding>`。加一条的大致步骤是「写规则类 → 注册进 `Rules.all()` → 加正反例 → 补文档和编号」。仓库里的 `docs/rules.md` 每节末尾都写了「判断范围」，照着那个粒度写，误报率才压得住。

有想要但还没覆盖的坑，开 issue 描述「什么代码、什么现象、为什么该算问题」就够了。
